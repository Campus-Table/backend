# 시연 시뮬레이터 (`demo/`)

서버 밖에서 도는 **외부 클라이언트**입니다. 서버 JAR에는 포함되지 않고, 운영 코드를 바꾸지 않습니다.
가상 인물이 실제 API로 주문하고 식사하며, 그 결과를 혼잡도(인원 스냅샷)로 보냅니다.
시연자가 사용자 화면에서 직접 결제·주문하면 같은 인원/대기열에 합쳐집니다.

## 동작

```
가상 인물 (10,000명 프로필, 시드로 생성)
  로그인 -> 주문 -> 도착 인증 -> 조리 대기 -> 음식 나옴 -> [자리가 나면] 식사 -> 퇴장
                                                  ^                 |
                                    좌석 220 초과 시 자리 대기      v
앉아 먹는 인원 + 시연자(실제 사용자) 인원 -- 20초마다 --> POST /occupancy (SIMULATION)
```

- **혼잡도 = 앉아서 먹는 사람만** 셉니다(조리 대기 중인 사람은 제외). 좌석을 넘으면 음식이 나온 사람이 자리 대기를 하고, 이용률은 100%에서 멈춥니다.
- **목표 이용률 곡선**(프리셋)을 따라 도착 속도를 자동 조절합니다. 도착은 포아송 랜덤이고, 최대 **30초에 4명**(가상 시간 기준)입니다.
- **실제 사용자 합산**: 관리자 주문 조회에서 시연 계정(학번 `99xxxxxx`)이 아닌 주문을 읽어, 음식이 나온 뒤 식사 시간(식당 설정, 기본 30분) 동안 인원에 더합니다. 실제 사용자는 자리 대기에서 우선합니다.
- **가게 평균 대기시간**을 시연 중 1분으로 낮추고(`--avg-wait`), 종료할 때 원래 값으로 복원합니다. 원래 값은 `demo/.state.json`에 저장됩니다(비정상 종료 시 `--restore`).
- **no-show**: 기본 5%는 도착 인증을 하지 않아 1시간 뒤 자동 취소·100% 환불됩니다.
- 시뮬레이터를 끄면 스냅샷이 끊기고, 5분 뒤 혼잡도는 주문 기반 값으로 돌아갑니다.

## 준비 (한 번)

1. 서버가 떠 있고 식당·가게·메뉴 시드가 들어가 있어야 합니다(`SEED_ENABLED=true` 또는 `seed.sql`).
2. 시연 계정 300개를 DB에 넣습니다(학번 `99000001`~`99000300`, 비밀번호 `Demo!2345`, 잔액 1천만 P).
   ```bash
   mysql -h <DB> -u <USER> -p campus_table < demo/users.sql
   ```
   **운영 서비스용 DB에는 넣지 마세요.** 시연용 환경에서만 실행합니다. 가입은 메일 인증이 필요해 API로는 만들 수 없습니다.
3. 식당 좌석이 220석인지 확인합니다(기존 DB는 `PATCH /api/admin/cafeterias/{id}` `{"seatCount":220}`).

## 실행

```bash
export DEMO_ADMIN_SN=<관리자 학번>
export DEMO_ADMIN_PASSWORD=<관리자 비밀번호>        # 파일/명령줄에 적지 마세요
python demo/sim.py --target http://localhost:8080 --preset lunch
```

Python 3.9+ 표준 라이브러리만 사용합니다. 시작할 때 **시드**가 출력되며, 같은 시나리오는 `--seed 123`으로 재생합니다.

| 옵션 | 기본 | 설명 |
|---|---|---|
| `--target` | `http://localhost:8080` | 서버 주소 |
| `--preset` | `lunch` | `lunch` 65분(여유 -> 피크 약 92% -> 여유, 끝나면 종료), `quiet` 한가함 유지, `packed` 약 90% 유지, `overflow` 목표 120%(좌석이 차면 자리 대기, 이용률 100% 고정) |
| `--speed` | 1 | 가상 시간 배속. 식사 시간·곡선만 빨라지고 서버의 조리 시간은 실제 시간이라 **3 이하 권장** |
| `--minutes` | 프리셋 | 이 가상 분 뒤 종료 |
| `--avg-wait` | 1 | 시연 중 가게 평균 대기시간(분). 0이면 건드리지 않음 |
| `--eat-median` | 25 | 식사 시간 중앙값(가상 분). 늘리면 같은 도착 속도에서 인원이 더 쌓임 |
| `--interval` | 20 | 스냅샷 전송 간격(초). 서버 유효시간 300초보다 짧아야 함 |
| `--pool` | 300 | 사용할 시연 계정 수 |
| `--noshow` | 0.05 | 도착 인증을 안 하는 비율 |
| `--max-rate` | 4/30 | 가상 초당 최대 도착 인원 |
| `--restore` | | 비정상 종료 후 가게 평균 대기시간만 복원 |

`Ctrl+C`로 멈추면 평균 대기시간을 복원합니다. 진행 중이던 가상 주문은 그대로 남습니다.

## 시연 흐름 예

1. 시뮬레이터를 `lunch`로 시작 -> 사용자 화면의 혼잡도가 20초마다 부드럽게 올라갑니다.
2. 시연자가 사용자 화면에서 충전(토스 테스트) -> 가게 주문 -> 관리자 화면에서 현장 번호 확인 후 도착 인증.
   가상 주문과 같은 가게 대기열에 들어가므로 대기번호·예상 시간이 이어집니다.
3. 음식이 나온 시연자는 식사 시간 동안 혼잡도 인원에 포함됩니다.

## 정리

```bash
mysql ... campus_table < demo/cleanup.sql
```
시연 계정의 주문·알림·마일리지 내역과 `SIMULATION` 스냅샷을 지우고 잔액을 채웁니다(실제 사용자 데이터는 건드리지 않음).

## 한계

- 서버는 가게마다 평균 대기시간에 1건씩 처리하는 모델이라(예상 대기 = (앞 인원+1) x 평균 대기시간), 도착 속도는 `0.85 x 가게 수 / 평균 대기시간`을 넘지 못하게 자동 제한합니다(가게 9개, 1분이면 약 7.6건/분). 그래서 한 번에 쌓이는 인원은 `도착 속도 x (식사 시간 + 조리 대기)` 정도이고, 220석에서 90% 안팎에 도달합니다. 더 채우려면 `--eat-median`을 늘리거나 `overflow` 프리셋을 쓰세요.

- 서버가 여러 대(Auto Scaling)여도 클라이언트는 ALB 주소 하나로 접속하므로 동작은 같습니다.
- 가상 인물은 계정 풀을 돌려 씁니다. 동시 주문이 300을 넘으면 `풀부족`이 로그에 찍히고 그 도착은 건너뜁니다.
- 배속을 올리면 서버의 조리 시간(실제 분)이 가상 시간으로는 길어져 목표 이용률에 못 미칠 수 있습니다.
- 학번 `99xxxxxx` 범위를 시연 계정으로 씁니다. 실제 사용자 학번과 겹치면 안 됩니다.
